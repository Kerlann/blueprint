# Story 1.2 : Types de pins et système de types

## Status

Ready for Review

## Story

**En tant que** développeur du mod,
**je veux** un registre de `PinType` avec des règles d'assignabilité et de conversion,
**afin que** le validateur puisse accepter ou refuser un lien de façon déterministe et explicable.

## Acceptance Criteria

1. Types de base fournis : `exec`, `bool`, `int`, `long`, `double`, `string`, `vec3`, `blockpos`, `direction`, `itemstack`, `entity`, `player`, `blockstate`, `resourcelocation`, `text`, `any`.
2. Les types paramétrés `list<T>` et `map<K,V>` sont représentables et comparables.
3. `PinType.isAssignableFrom(other)` implémente les conversions implicites déclarées : `int → long → double`, `player → entity`. Aucune autre coercition implicite.
4. Chaque `PinType` porte une couleur ARGB, une `PinShape`, une clé de traduction, un `Codec` et un `StreamCodec` pour ses littéraux.
5. Le type joker `any` se résout au câblage ; un `GenericGroup` déclaré sur un nœud propage la résolution à tous les pins du même groupe.
6. `PinTypeRegistry` refuse un identifiant en doublon avec un message nommant les deux fournisseurs, et se fige (`freeze`) après la phase d'enregistrement.
7. Un `PinType` enregistré sans `Codec` ou sans `StreamCodec` provoque une exception **au démarrage** (message nommant le mod fautif).
8. Tests unitaires couvrant la matrice complète d'assignabilité, y compris jokers, génériques imbriqués (`list<list<int>>`) et cas négatifs.

### Data Models

- `PinType` : interface publique avec `id()`, `javaType()`, `color()` (ARGB), `shape()`
  (`EXEC`, `CIRCLE`, `DIAMOND`, `ARRAY`, `MAP`), `translationKey()`,
  `isAssignableFrom(PinType)`, `defaultValue()` [Source: architecture.md#3.2]
- Coercitions implicites : graphe de coercition déclaré, fermeture transitive calculée au
  `freeze` ; `int → long → double`, `player → entity` ; `T → list<T>` **interdite**
  [Source: architecture.md#3.2]
- Génériques `list<T>` / `map<K,V>` : **invariants** (pas de covariance — piège d'écriture)
  [Source: architecture.md#3.2]
- Joker `any` : résolu au câblage ; groupe de jokers propagé à tous les pins du même
  groupe dans le nœud [Source: architecture.md#3.2]
- `LiteralValue` encodée par le `Codec` fourni par le `PinType` ; les mods tiers
  fournissent le codec de leurs types [Source: architecture.md#3.4]

### API Specifications

- Contrat public consommé par les mods tiers : `PinType.builder(id)` avec `.javaType`,
  `.color`, `.shape`, `.translationKey`, `.codec`, `.streamCodec`, `.coerceFrom`
  [Source: extension-api.md#3] — la signature livrée ici **est** celle documentée là-bas ;
  toute divergence doit mettre à jour les deux documents.
- Sans `codec`, l'enregistrement est **refusé au démarrage** (jamais de perte de données
  en jeu) [Source: extension-api.md#3]

### Technical Constraints

- Mappings **Mojang** : `ResourceLocation`, `BlockPos`, `Vec3`, `Direction`, `ItemStack`,
  `BlockState`, `Component`, `Entity`, `ServerPlayer` — jamais les noms Yarn
  [Source: architecture/tech-stack.md#nommage-mojang]
- Types de l'`api` **immuables**, collections via `List.copyOf`/`Map.copyOf`
  [Source: architecture/coding-standards.md#3]
- Ne pas appeler de registre Minecraft à la construction d'un `PinType` : les tests de
  `core` tournent sans Minecraft démarré [Source: architecture/coding-standards.md#7]
- Erreur de développeur (type incomplet, doublon) → exception au démarrage nommant le mod ;
  jamais en jeu [Source: architecture/coding-standards.md#4]
- Palette de couleurs par défaut alignée sur le thème de l'éditeur
  [Source: ux-ui-spec.md#12] ; lisibilité deutéranopie/protanopie doublée par la forme
  (NFR11) [Source: prd.md#2.2]

### Décisions à respecter (rappels non couverts ailleurs)
