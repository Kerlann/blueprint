# Story 9.1a : Débogueur — cœur serveur (points d'arrêt, pas-à-pas, valeurs)

## Status

Done

## Story

**En tant qu'** auteur de blueprint dont le graphe ne fait pas ce qu'il croit,
**je veux** l'arrêter sur un nœud et voir les valeurs qui y passent,
**afin de** comprendre où ça dérape au lieu de deviner.

## Acceptance Criteria

1. **Points d'arrêt** sur un nœud : l'exécution s'arrête **avant** que le nœud tourne,
   et y reste jusqu'à `step` ou `continue`.
2. **Pas-à-pas** : un `step` exécute exactement un nœud, puis s'arrête au suivant.
3. **Valeurs** : dernières entrées et sorties vues sur chaque nœud, plus le nombre de
   passages et une trace bornée des nœuds parcourus.
4. **Réservé aux administrateurs** : `/blueprint debug` suit la permission configurée —
   voir les valeurs d'un graphe, c'est voir ce que fait le joueur qui l'a écrit.
5. **Coût nul quand personne ne débogue** : une lecture de `volatile boolean` par
   exécution, aucune table consultée, aucune allocation.

## Découpage

La story 9.1 du PRD couvre aussi le rendu (surlignage du flux, pulsation des liens,
valeurs affichées sur les pins dans l'éditeur). C'est **9.1b** : elle a besoin de
paquets et du canevas, alors que tout ce qui suit se teste sans lancer le jeu.

## Dev Agent Record

- claude-fable-5 — `DebugSessionTest` (8) vert, build complet vert.
- **Le point dur : arrêter sans figer.** La VM ne peut pas « bloquer » — elle rendrait
  la main au serveur avec un thread occupé. Un arrêt se traduit donc par
  `Suspended(1)` **sans avancer le pc** : le tick suivant repasse exactement au même
  endroit, le nœud n'a toujours pas tourné, et l'ordonnanceur existant fait tout le
  travail. Aucune modification de l'ordonnanceur, aucune reprise à inventer.
- **La machine à états tient en trois cas** (`pauseBefore`) : déjà en pause → on le
  reste (sinon le nœud repartirait seul au tick suivant) ; nœud tout juste relâché →
  il passe une fois (sinon un point d'arrêt se rearmerait sur lui-même et rien
  n'avancerait) ; sinon → point d'arrêt ou pas-à-pas armé. Les deux premiers cas sont
  exactement ceux que les tests ont fait apparaître.
- **Coût nul** : `DebugSessions.active()` est un `volatile boolean` lu **une fois par
  exécution** dans `runMeasured`. Rien dans la boucle chaude, rien par instruction.
- **Les valeurs sont rendues en texte à l'instant où elles passent**, bornées à 64
  caractères : retenir une entité vivante ou un `ItemStack` dans une session la ferait
  survivre au déchargement du monde. Un test vérifie que la table ne contient que du
  texte.
- **Ce que le nœud a VU, pas ce qui était câblé** : `NodeContextImpl` note les entrées
  effectivement lues (défaut de pin ou de type compris) — seulement quand le débogage
  est actif, via un drapeau passé par la VM.
- **Fermer le débogueur libère une exécution en pause** : sinon un blueprint resterait
  figé pour toujours parce qu'un joueur a quitté son débogueur. Test dédié.
- `/blueprint debug <id> on|off|status|step|continue|clear|break <nœud>|unbreak|values` ;
  les nœuds se désignent par un **préfixe d'UUID** (8 caractères suffisent), suggéré
  depuis la trace — taper un UUID complet dans le chat est impraticable. Un préfixe
  ambigu est refusé plutôt que deviné.
- 13 clés de langue (en + fr).
- **VERIFY-9.1a** (session finale) : `/blueprint debug blueprint:demo on`, poser un point
  d'arrêt sur un nœud vu dans la trace, déclencher le graphe → l'exécution s'arrête,
  `values` montre les entrées/sorties, `step` avance d'un nœud, `continue` termine.
