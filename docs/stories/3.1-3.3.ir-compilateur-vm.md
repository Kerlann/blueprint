# Stories 3.1 + 3.2 + 3.3 : IR, compilateur et VM (jalon exécutable)

## Status

Done

## Story

**En tant que** projet,
**nous voulons** compiler un graphe en représentation intermédiaire et l'exécuter dans une VM bornée,
**afin qu'** un blueprint s'exécute réellement, de façon déterministe, mesurable et impossible à faire diverger.

> Livraison groupée assumée : l'IR, le compilateur et la VM ne se prouvent qu'ensemble
> (compiler un graphe réel et l'exécuter). Les stories 3.4 (suspension persistée) et
> 3.5 (ordonnanceur) suivent séparément.

## Acceptance Criteria

**3.1 — IR**
1. Jeu d'instructions défini et documenté : `Const`, `Call` (table de sauts exec intégrée), `Jmp`, `JmpIf`, `LoadVar`, `StoreVar`, `Yield`, `Return` — interface scellée, un `switch` exhaustif côté VM. ⚠ Écart assumé : `FRAME_PUSH/POP` différés avec les fonctions utilisateur (v1.1) — l'interface scellée s'étend sans casser.
2. Chaque instruction porte l'UUID du nœud source (diagnostic, débogage) — nul pour les instructions synthétiques.
3. L'IR est sérialisable (NBT) pour un futur cache : round-trip testé, types résolus via le registre au décodage.

**3.2 — Compilateur**
4. `Compiler.compile(blueprint, registry, startNode)` : validation d'abord (erreurs → échec avec diagnostics ciblés, jamais d'exception) ; linéarisation du flux exec avec fusion (nœud déjà émis → cible directe, les boucles exec deviennent des arêtes arrière) ; slot par pin de sortie de données.
5. Les nœuds purs sont émis avant leur consommateur, une fois par position (mémoïsation FR13) ; les littéraux/défauts deviennent des `Const` dédupliqués.
6. Compilation d'une chaîne de 1 000 nœuds < 50 ms (NFR2), mesurée et consignée par le test.

**3.3 — VM**
7. `BlueprintVm.run(ir, state, env, fuelBudget)` : machine à slots, statuts `DONE | SUSPENDED(ticks) | OUT_OF_FUEL | FAULTED(nœud, message)` — le fuel épuisé préserve l'état et l'exécution reprend au run suivant.
8. Le coût en fuel d'un `Call` est le `fuelCost` du nœud ; une boucle infinie épuise le budget au lieu de figer (testé) ; **aucune exception ne s'échappe** : une action qui lève → `FAULTED` nommant le nœud (coding-standards §1.5).
9. `ctx.suspend(ticks)` pendant un `Call` → `SUSPENDED`, reprise à la cible exec du nœud ; `ctx.fail` → `FAULTED` propre ; **CTX-001 tranché** : un pin d'entrée sans valeur ni défaut → `FAULTED` nommant le pin (plus jamais de null silencieux).
10. Tests : IR manuelle (boucle décrémentante LoadVar/StoreVar/JmpIf, boucle infinie + fuel, reprise), graphes réels compilés (chaîne testmod, branches des deux côtés, purs mémoïsés, ordre d'exécution vérifié par nœud espion).

## Dev Notes

- Le `Call` EST la table de sauts : les branches des nœuds de flux (`ctx.exec`) se
  résolvent par `execTargets[pin] → index` (cible < 0 = fin d'exécution) — pas de
  `JmpIf` généré par les graphes ; `Jmp`/`JmpIf` servent l'IR manuelle et les futures
  constructions du générateur BScript.
- Pas encore de nœuds Get/Set de variables (FR9, synthèse ultérieure) : `LoadVar/StoreVar`
  sont couverts au niveau IR ; le graphe les émettra quand ces nœuds existeront.
- L'entrée d'exécution est un nœud de départ explicite : les événements réels (7.6)
  fourniront les points d'entrée ; le `startNode` vient d'eux ou du testeur.
- Résolution des `NodeType` à l'exécution via `ExecutionEnvironment` (l'IR ne référence
  que des identifiants — condition de la sérialisabilité et des fantômes).
- Fuel : budget passé par le caller (l'ordonnanceur 3.5 décidera des budgets) ;
  profondeur de frames différée avec les frames elles-mêmes.
