# Story 2.1 : NodeType et builder

## Status

Ready for Review

## Story

**En tant que** développeuse de mod tiers,
**je veux** déclarer un type de nœud par un builder fluide,
**afin d'** exposer une action de mon mod aux joueurs en ~10 lignes, sans dépendre du code interne de Blueprint.

## Acceptance Criteria

1. `NodeType.builder(id)` expose `.category`, `.exec()`, `.execIn/.execOut`, `.in` (avec et sans défaut), `.out`, `.pure()`, `.generic`, `.side`, `.permission`, `.fuelCost`, `.deterministic`, `.action`, `.build` — la signature documentée dans `extension-api.md` §2.2.
2. Un `NodeType` est immuable et décrit intégralement ses pins (`PinSpec` : nom, nature, type, défaut).
3. Les pins d'entrée acceptent une valeur par défaut **typée** : un défaut du mauvais type Java lève au `build()`, pas en jeu.
4. Toute incohérence lève une exception explicite au `build()` (démarrage), jamais en jeu : `pure()` + pins exec, deux pins de même nom sur un même côté, ni `pure()` ni pin exec, `action` manquante, joker utilisé dans un pin sans être déclaré par `.generic()`.
5. Javadoc complète sur tous les types publics ajoutés (`NodeType`, `NodeAction`, `NodeContext`, `NodeCategory`, `ExecSide`).
6. `NodeContext` (interface consommée par les actions) est figée dans sa forme minimale — `in/out/exec/suspend/fail/server/level/logger` ; `blueprint()`/`trigger()` arriveront avec leurs types (2.3/2.5) sans casser les consommateurs.

- Noms de pins uniques **par côté** (une entrée et une sortie peuvent partager un nom — les liens sont orientés).
