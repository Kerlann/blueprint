# Stories 7.1a + 7.2 + 7.6 : Bibliothèque standard et événements du monde

## Status

Done

## Story

**En tant que** joueur,
**je veux** des nœuds standard (flux, maths, logique, chaînes) et des événements du monde qui déclenchent mes blueprints,
**afin qu'** un graphe réagisse à un vrai événement de jeu et calcule réellement — le produit devient jouable.

> Découpage assumé : les nœuds de flux **structurés** (`sequence`, `while`, `for`,
> `for_each`, `gate`, `do_once`, `switch`, `wait_until`) exigent des continuations
> (frames VM, différées en v1.1 dès la 3.1) → story dédiée « 7.1b flux structuré +
> frames ». Les nœuds monde/entité/joueur/item (7.3-7.5) manipulent le `ServerLevel`
> et se vérifient en gametest → stories séparées après le spike 1.6.

## Acceptance Criteria

1. **7.1a — Flux de base** : `blueprint:flow/branch` (bool → true/false), `flow/select` (ternaire pur générique `T`), `flow/wait` (ticks, ≥ 1), `flow/return` (terminal) — comportement testé nœud par nœud.
2. **7.2 — Purs** : ~30 nœuds `math/*` (arith. double, min/max/abs/round), `logic/*` (comparaisons, booléens, equals/not_equals sur `any`), `string/*` (concat, length, contains, upper, lower), `convert/*` (to_string, to_int), `math/random` (déterministe : même graine + index → même valeur), `debug/log`. **Division/modulo par zéro → `ctx.fail` traduit, jamais d'exception** (AC PRD).
3. Les valeurs numériques suivent les coercitions au runtime : un littéral `int` câblé sur un pin `double` est adapté par le contexte (`Number` → type attendu) — sans ça, chaque graphe mathématique fauterait.
4. **7.6 — Événements** : les 9 `EventType` standard déclarés (`server_tick`, `player_join`, `player_quit`, `player_use_block`, `player_use_item`, `player_break_block`, `entity_death`, `player_chat`, `signal`) ; ponts Fabric fins câblés dans `BlueprintMod` (vérification en jeu/gametest) ; `signal` émis par graphe = story ultérieure (nœud émetteur).
5. **Nœuds d'événement synthétisés** : chaque `EventType` (standard OU tiers) engendre automatiquement un `NodeType` point d'entrée (catégorie EVENT, `entryPoint`, sorties = charge utile, action = matérialisation du `trigger` dans les slots) — les mods gagnent leurs nœuds déclencheurs gratuitement.
6. **Le pont événement → ordonnanceur** : à l'émission d'un événement, chaque blueprint **actif** contenant un nœud de cet événement est compilé (cache par révision) et lancé sur l'ordonnanceur — testé de bout en bout headless : `fire(server_tick)` → graphe → nœuds standard → enregistrements espions ; un événement à charge utile alimente le graphe via le nœud d'événement.
7. Enregistrement standard sous le fournisseur « blueprint », opt-in (`loadFromFabric` l'inclut, `load()` des tests reste nu) ; clés de langue en/fr pour tous les nœuds et événements standard.

## Dev Notes

- Le nœud d'événement N'EST PAS le déclencheur : c'est un marqueur + matérialisateur de
  charge utile. Le déclenchement vient du bridge abonné au dispatcher (2.5) — paresse
  conservée (aucun blueprint abonné à un événement = payload jamais construite… le bridge
  s'abonne par événement seulement s'il existe ; abonnement global simple accepté en MVP,
  le filtre enabled fait le reste).
- `server_tick` émis chaque tick : le coût sans blueprint concerné = une lecture de map
  (paresse 2.5) — mesuré acceptable.
- Ponts Fabric : `UseBlockCallback`/`UseItemCallback` retournent `InteractionResult.PASS`
  toujours (le graphe observe, il n'annule pas — l'annulation viendra avec un retour
  d'événement, hors MVP).
- Leçon VM-COMP-001 : `select` est pur et générique — vérifier son comportement dans les
  deux branches d'un branch.
