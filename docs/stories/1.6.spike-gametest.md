# Story 1.6 : Spike — infrastructure gametest

## Status

Done

## Story

**En tant que** équipe,
**je veux** une infrastructure de tests en jeu (gametest serveur) opérationnelle sur le framework 1.21.11,
**afin de** vérifier automatiquement ce que les tests headless ne peuvent pas atteindre : enregistrement réel des commandes, entrypoints, et bientôt exécution de blueprints (épics 3 et 7).

## Contexte (pourquoi un spike)

Le framework gametest a été **refondu en données** en 1.21.5 : l'annotation `@GameTest`
n'existe plus dans le JAR 1.21.11 (vérifié au javap en story 1.5), les tests passent par
des environnements de test déclarés et `GameTestHelper` a changé de surface. La méthode
d'intégration Fabric correspondante (`fabric-gametest-api-v1` post-refonte) est à
découvrir — c'est l'objet du spike. Origine : AC5 de la 1.5 (ajusté) + gate QA TEST-002.

## Acceptance Criteria

1. `./gradlew runGametest` (ou tâche équivalente) démarre un serveur headless, exécute les gametests et **échoue le build** si un test échoue.
2. Un premier gametest de fumée vérifie l'init du mod (logs entrypoints) et l'exécution réelle de `/blueprint create|list|info|disable|delete` via `performPrefixedCommand`, messages inclus (ferme VERIFY-002).
3. Un second gametest vérifie `runClient`-équivalent côté serveur intégré si le framework le permet — sinon documenter la limite (VERIFY-001 reste manuel dans ce cas).
4. La méthode (environnements de test, enregistrement Fabric, structure des classes) est documentée dans `docs/architecture/tech-stack.md` pour les stories suivantes (3.x, 7.x).
5. La tâche gametest est exclue du `build` par défaut (elle démarre un serveur) mais exécutable en CI sur demande.

### Agent Model Used

claude-fable-5 — spike conclu **positivement** : l'infrastructure marche, 5 tests passent
dans un serveur réel en ~1,1 s de temps de jeu.

### Completion Notes List

- **Ce que la refonte a changé, concrètement** : l'annotation est celle de Fabric
  (`net.fabricmc.fabric.api.gametest.v1.GameTest`), les méthodes sont **publiques et non
  statiques** avec un seul paramètre `GameTestHelper`, et la découverte passe par
  l'entrypoint **`fabric-gametest`** du `fabric.mod.json` (la classe listée est
  instanciée, ses méthodes annotées sont ramassées). Structure par défaut : une zone
  vide 8×8 fournie par Fabric — aucun fichier de structure à écrire.
- **Lancement** : `./gradlew runGametest` — serveur dédié sans fenêtre, rapport JUnit
  dans `build/gametest/report.xml`, **code de sortie non nul si un test échoue**. La
  configuration Loom est un run `server()` avec `-Dfabric-api.gametest=true` (AC1, AC5 :
  la tâche n'est pas dans `build`).
- **Module dédié `gametest`** plutôt que le testmod : le testmod ne dépend que de `api`
  — c'est sa raison d'être — alors que ces tests doivent voir `core`.
- **Piège trouvé, et corrigé : les tests s'empoisonnaient entre eux.** Un test qui
  échoue ne nettoie pas son blueprint ; la persistance (6.1) le **restaure au démarrage
  suivant**, il se déclenche pendant les tests d'après et les fait échouer à leur tour.
  Un run rate, tous les suivants ratent. `runGametest` efface donc le monde avant
  chaque lancement — un test en jeu doit partir d'un monde neuf, comme un test unitaire
  part d'un objet neuf.
- **Deuxième piège** : `helper.relativePos(helper.absolutePos(p))` ne rend pas `p` (le
  repère du test est orienté). Les assertions interrogent le monde à la position
  **absolue** que le graphe a écrite.
- Amélioration tirée du spike : le pont d'événements journalisait « 1 diagnostic(s) »
  sans dire lequel. Il nomme maintenant le premier — c'est ce qui a permis de
  diagnostiquer en une seconde le refus `PERMISSION_EXCEEDED [WORLD, GAMEPLAY]` du
  premier test (un graphe qui pose un bloc doit relever son plafond).
- **Ce que les 4 tests couvrent** (et les VERIFY qu'ils remplacent) :
  | Test | Ce qu'il prouve | VERIFY remplacé |
  |---|---|---|
  | `aWorldEventRunsTheGraph` | événement réel → pont → compilation → VM → ordonnanceur → **bloc posé dans le monde** | VERIFY-004 (démo) |
  | `theBpcCommandTriggersItsBlueprint` | `/bpc <nom>` exécuté par le dispatcher réel déclenche le graphe qui le déclare | VERIFY-7.7 |
  | `persistenceGivesBackWhatItTook` | le vrai `SavedData` du monde encode et rend le blueprint à l'identique | VERIFY-005 (partiel : le redémarrage reste manuel) |
  | `anAdminNodeLeavesAnAuditTrail` | NFR15 en conditions réelles | VERIFY-9.3 |
- Limite assumée (AC3) : pas de client dans ce harnais — tout ce qui est **visuel**
  (éditeur, rendu, ergonomie) reste à voir de ses yeux. C'est exactement ce que la
  session finale doit regarder, et rien d'autre.
