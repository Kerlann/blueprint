# Story 6.2 : Synchronisation du registre au login

## Status

Done

## Story

**En tant que** joueur sur un serveur qui a des mods que je n'ai pas,
**je veux** que le client reçoive la description des nœuds du serveur,
**afin de** voir, câbler et éditer ces nœuds comme les autres — sans installer leurs mods.

## Acceptance Criteria

1. Au login, le serveur annonce le **hash** de son registre ; le client ne demande les
   descripteurs **que** s'il diverge du sien (FR35). Registres identiques (solo, ou
   client et serveur avec les mêmes mods) : zéro octet de descripteur sur le fil.
2. Envoi **fragmenté et compressé** — testé avec **5 000 descripteurs** : plusieurs
   fragments, chacun sous la borne de 28 000 octets, réassemblage et décodage exacts.
3. Un client sans les mods du serveur voit et câble quand même les nœuds concernés :
   les formes déduites des descripteurs reçus sont **identiques, nœud par nœud**, à
   celles que le serveur valide.

## Dev Agent Record

- claude-fable-5 — `DescriptorSyncTest` (6) + `ClientNodeRegistryTest` (2) verts,
  build complet vert (119 tests client, suite core complète).
- **Protocole** : trois paquets dans `core/net/BlueprintPayloads` —
  `registry_hash` (S2C, au JOIN), `registry_request` (C2S), `descriptor_chunk`
  (S2C, `index`/`total`/`byte[]`). Enregistrés dans l'init commune : le client
  déclare les mêmes types, un client vanilla ne reçoit rien (`canSend` gardé).
- **Sérialisation** (`core/net/DescriptorSync`, pure et testable sans réseau) :
  tous les descripteurs dans une `ListTag` → `NbtIo.writeCompressed` → découpe en
  fragments de 28 000 octets (les paquets custom plafonnent à 32 Kio). Le flux et
  le hash sont calculés **une fois** et mis en cache — les registres sont gelés
  après l'init.
- **Une livraison par connexion** : la seconde demande d'un même joueur est ignorée
  (le registre est gelé, elle ne peut rien apporter) ; l'ensemble est purgé à la
  déconnexion. Le vrai budget par joueur est l'affaire de la 6.4.
- **AC3** : `ClientNodeRegistry.of(descripteurs).lookup()` reproduit la règle
  `required` de `NodeRegistryImpl.toShape` — une entrée DATA sans défaut de pin ni
  défaut de type doit être câblée. Le test compare les deux formes pour **chaque**
  nœud de la bibliothèque standard, après un vrai aller-retour sur le fil : l'éditeur
  ne peut pas accepter un lien que le serveur refuserait.
- **Types de pins absents du client** : la synchro fabrique un type **opaque** (même
  identifiant, sans littéral, compatible avec lui seul) plutôt que de jeter le
  descripteur entier. Un descripteur indéchiffrable est sauté avec un avertissement,
  jamais propagé à moitié ; un flux tronqué échoue en silence (aucune synchro), pas
  en exception.
- `NodeDescriptor` gagne `entryPoint` (11ᵉ composant, ancien constructeur conservé) :
  sans lui le client prendrait un nœud d'événement pour un nœud ordinaire. Le champ
  entre aussi dans `canonical()`, donc dans le hash.
- L'éditeur consulte `RegistrySync.descriptors()` / `RegistrySync.lookup()` :
  descripteurs et vue validateur viennent **toujours de la même source**, jamais d'un
  mélange local/serveur.
- **VERIFY-6.2** (session finale) : serveur dédié avec un mod de nœuds absent du
  client → le log client annonce « Registre serveur divergent … », l'éditeur montre
  les nœuds du mod dans la palette et les câble. En solo, le log annonce « identique ».
