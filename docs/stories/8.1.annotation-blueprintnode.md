# Story 8.1 : Annotation `@BlueprintNode`

## Status

Done

## Story

**En tant qu'** auteur d'un mod tiers,
**je veux** déclarer un nœud en annotant une méthode statique,
**afin de** ne pas écrire de builder pour chaque nœud trivial.

## Acceptance Criteria

1. Annoter une méthode statique dérive automatiquement les pins depuis la signature :
   nom du paramètre → nom du pin, type Java → `PinType`, valeur de retour → pin de
   sortie ; `@In` nomme un pin et porte sa valeur par défaut, `@Out` nomme la sortie.
2. Faute de processeur d'annotations, un **scan des classes déclarées** prend le relais :
   `AnnotatedNodes.register(registry, MyNodes.class)` depuis un plugin, **ou** la clé
   `"blueprint:node_holders"` du `fabric.mod.json` — un mod peut n'avoir aucune classe
   de plugin.
3. Les erreurs de déclaration sont signalées avec un message qui **nomme la méthode**
   et n'affectent que le mod fautif (isolation existante de `PluginLoader`).
4. Documentation et exemple complet dans `docs/extension-api.md` ; le mod d'exemple
   `testmod` déclare un nœud par cette voie.

## Déviation assumée

Le **processeur d'annotations** (AC2 « optionnel ») n'est pas livré : il imposerait une
étape de build aux mods tiers pour un gain qui se limite au moment où l'erreur apparaît
(javac plutôt que démarrage du jeu). Le scan couvre le même besoin, y compris sans
classe de plugin. Consigné v1.1 — l'annotation et le binder sont conçus pour qu'un
processeur puisse générer exactement les mêmes `NodeType`.

Une méthode annotée n'a qu'**un** pin de sortie (sa valeur de retour). Les sorties
multiples passent par le builder : les émuler demanderait des paramètres « boîte »
(`IntRef`…) qui rendraient la signature moins lisible que le builder qu'ils remplacent.

## Dev Agent Record

- claude-fable-5 — `AnnotatedNodesTest` (11) vert, `PluginLoaderTest` étendu, build complet vert.
- Le binder vit dans **`api`** (`fr.blueprint.api.annotation.AnnotatedNodes`) : un mod
  tiers ne dépend que de `api`, il doit donc y trouver de quoi enregistrer ses nœuds.
- **Le nom des pins vient du paramètre** — et `-parameters` est activé pour tout le
  projet. Sans cette option chez le mod tiers, la dérivation **refuse** au lieu de
  produire des pins `arg0`/`arg1` : un nom de pin ne se corrige plus une fois qu'il est
  dans les graphes des joueurs. Le message dit quoi faire (option de compilation ou
  `@In("nom")`).
- Un paramètre `NodeContext` est **injecté** et n'apparaît pas comme pin : un nœud
  annoté garde donc accès au serveur, au déclencheur et à `fail()`.
- Valeurs par défaut : `@In(def = "10")` est lu selon le type du pin (int, long, double,
  booléen, texte). Un type sans lecture évidente est refusé plutôt que deviné.
- Types de pins d'un mod tiers : table `Map<Class<?>, PinType>` passée à
  `register` — le message d'erreur d'un type inconnu montre l'appel exact à écrire.
- Ordre de dérivation **trié par nom de méthode** : `getDeclaredMethods()` ne garantit
  aucun ordre, et le hash de registre (6.2) doit être stable entre deux démarrages.
- `PluginLoader` gagne une phase « 2 bis » pour les classes déclarées ; une classe
  introuvable ou fautive passe par l'isolation existante — test dédié avec un mod sain
  à côté.
- L'exception levée par le corps du nœud remonte **telle quelle** (déballage de
  `InvocationTargetException`) : la VM la journalise avec le nœud fautif, la pile du
  proxy réflexif n'apporterait rien.
- `testmod` déclare `blueprint_testmod:shout` par annotation — `PluginLoaderTest`
  vérifie qu'il arrive par le même chemin, avec le même fournisseur.
- **VERIFY-8.1** (session finale) : `shout` visible dans la palette de l'éditeur, avec
  ses défauts « salut » et 1.
