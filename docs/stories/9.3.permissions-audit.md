# Story 9.3 : Permissions, quotas configurables et audit

## Status

Done

## Story

**En tant qu'** administrateur de serveur,
**je veux** régler les limites de Blueprint et savoir qui exécute des nœuds sensibles,
**afin de** l'ouvrir à mes joueurs sans signer un chèque en blanc.

## Acceptance Criteria

1. **Plafond par blueprint** : un nœud plus exigeant que le plafond du graphe ne
   s'exécute pas, et le diagnostic dit ce qui dépasse.
2. **Config serveur** : nombre de nœuds, taille d'un graphe reçu, quotas
   d'enregistrement et de requêtes, audit — tous dans `config/blueprint/config.json`.
   Une valeur absurde est **ramenée dans les clous**, jamais obéie ; une valeur
   illisible n'emporte pas le reste du fichier.
3. **NFR15** : toute exécution d'un nœud `ADMIN` est journalisée avec **blueprint,
   nœud, acteur et horodatage**, dans le log serveur et dans un tampon relisible.
4. **Escalades refusées**, testées : nœud `ADMIN` sous plafond `GAMEPLAY`, plafond
   relevé par un client non opérateur, quota de nœuds dépassé.

## Dev Agent Record

- claude-fable-5 — `PermissionAuditTest` (9) vert, build complet vert.
- **L'audit est écrit AVANT l'exécution du nœud** : si le nœud fait tomber le serveur,
  la trace doit déjà exister. Hors `ADMIN`, le coût est une comparaison d'énumération.
- **L'acteur** vient de la charge utile du déclencheur (`player`) ; à défaut, c'est
  l'événement lui-même (un tick serveur n'a pas d'acteur). La lecture est protégée :
  un audit ne doit jamais casser une exécution.
- Le journal part dans un logger dédié (`blueprint-audit`, donc dans les logs de
  l'hébergeur) **et** dans un tampon borné de 200 entrées — le log seul serait
  illisible en jeu, le tampon seul disparaîtrait au redémarrage.
- **Les quotas ne sont plus des constantes** : `BlueprintConfig` rend un `GraphLimits`
  et un `NetLimits`, et `ServerBlueprintNet` construit ses seaux à jetons depuis la
  configuration. Les bornes structurelles héritées de 6.4 (liens, variables, textes,
  fantômes) restent aux valeurs par défaut : elles protègent le format, pas la
  politique du serveur.
- **Valeurs absurdes ramenées dans les clous** (`Math.max`) plutôt que refusées : un
  serveur qui écrit `maxNodes: 0` veut visiblement « peu », pas « rien » — et un mod
  qui refuse de démarrer sur une faute de frappe est pire que le problème.
- `intOr`/`boolOr` avalent une valeur illisible champ par champ (même leçon que
  DP-001 sur les datapacks) : `"fuelPerTick": "beaucoup"` ne doit pas rendre TOUTE la
  configuration au défaut sans le dire.
- **VERIFY-9.3** (session finale) : mettre `maxNodes: 5` dans la config, redémarrer,
  tenter d'ajouter un sixième nœud dans l'éditeur → refus ; exécuter un nœud ADMIN →
  ligne `blueprint-audit` dans le log serveur avec le nom du joueur.
