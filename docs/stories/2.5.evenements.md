# Story 2.5 : Événements enregistrables

## Status

Ready for Review

## Story

**En tant que** développeuse de mod,
**je veux** déclarer mes propres événements déclencheurs et les émettre depuis mon code,
**afin que** les joueurs réagissent à mes mécaniques avec leurs blueprints.

## Acceptance Criteria

1. `EventType.builder(id)` déclare des sorties de données typées (`out`), un mode de dispatch (`GLOBAL | PER_LEVEL | PER_PLAYER`) et des clés de traduction ; incohérences (sortie dupliquée, type exec) → exception au build.
2. `BlueprintEvents.fire(event, payload -> …)` déclenche tous les abonnés de l'événement ; la charge utile est validée contre les sorties déclarées (pin inconnu ou valeur mal typée → exception de développement nommant l'événement et le pin) et exposée aux abonnés via `TriggerContext.output(pin)`.
3. **Asynchrone-sûr** : un `fire` hors du thread serveur est reporté sur le thread serveur (testé avec une porte de thread factice) ; la façade `BlueprintEvents` est sans effet tant qu'aucun dispatcher n'est installé (démarrage) — jamais d'exception.
4. **Coût négligeable sans abonné** : le constructeur de charge utile n'est PAS invoqué si l'événement n'a aucun abonné (paresse prouvée par test — c'est la mesure).
5. `EventRegistry` complété (register/get/all), `EventRegistryImpl` avec fournisseur/gel/`removeAllFrom`, branché dans la phase 3 du `PluginLoader` (isolation comprise) ; `LoadedRegistries` expose le registre d'événements.
6. `TriggerContext` complété (`output(pin)`) — le placeholder de la 2.3 tient sa promesse de non-cassure.

## Dev Notes

- Façade `BlueprintEvents` : l'api ne référence jamais `core` — `core` installe son
  `EventSink` au démarrage du serveur (`ServerLifecycleEvents.SERVER_STARTING`), le
  retire à l'arrêt ; avant installation, `fire` est un no-op silencieux [Source: P5, checkApiIsolation].
- Porte de thread abstraite (`isOnThread`/`submit`) : en jeu `server.isSameThread()` /
  `server.execute` ; en test une porte factice à file — même leçon que Commands (1.5).
- Les abonnés réels (blueprints compilés) arrivent avec l'ordonnanceur (3.5) et les
  événements du monde (7.6) ; ici l'abonnement est une interface core (`EventSubscriber`).
- La paresse AC4 impose la signature `fire(EventType, Consumer<EventPayload>)` — ne
  jamais construire la charge utile avant d'avoir vérifié qu'il y a des abonnés.

### Completion Notes List

- **La paresse AC4 est structurelle, pas optimisée après coup** : `fire` teste
  l'abonnement avant toute chose — la signature `Consumer<EventPayload>` rend
  impossible de construire la charge utile pour rien. Le test le prouve par un
  compteur jamais incrémenté.
- La façade `BlueprintEvents` est le seul état statique mutable de l'api : volatile,
  no-op par défaut, installée/retirée par le cycle de vie serveur — un mod qui émet
  pendant l'init ou après l'arrêt ne casse rien.
- Un abonné fautif est journalisé et n'empêche pas les autres d'être servis (même
  philosophie que l'isolation des plugins).
- `TriggerContext.output` sur une sortie non déclarée lève (cohérent avec `ctx.in` de
  la 2.3) ; une sortie déclarée mais non renseignée rend null — la sémantique
  « renseignement obligatoire ? » sera tranchée avec CTX-001 en 3.3.
- `Dispatch` est déclaré mais pas encore exploité (l'ordonnanceur 3.5 filtrera par
  monde/joueur) — assumé, c'est du contrat public à figer maintenant.
