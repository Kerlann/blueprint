# Story 6.1 : Persistance dans la sauvegarde du monde

## Status

Ready for Review

## Story

**En tant que** joueur,
**je veux** que mes blueprints ET mes exécutions suspendues survivent au redémarrage du monde,
**afin que** `/blueprint demo` d'hier fonctionne encore demain — sans réimporter quoi que ce soit.

> Coordination : session parallèle sur l'épic 5 (client/) — cette story reste
> strictement dans core/ ; pulls fréquents.

## Acceptance Criteria

1. Blueprints et exécutions suspendues persistés via `SavedData` (API codec 1.21.5+ : `SavedDataType` + `Codec` via `CompoundTag.CODEC.xmap`), stockage de l'overworld, données vivantes tirées à l'encodage (manager + `captureForSave` non destructif — les sauvegardes périodiques n'arrêtent pas les exécutions).
2. Chargement au `SERVER_STARTED` avec **rapport** journalisé (chargés / corrompus préservés / reprises / annulées), jamais de crash : un blueprint indécodable est **préservé brut** et ré-émis à la sauvegarde (P4) ; une exécution irrésoluble (référence morte, blueprint absent, révision divergente, événement disparu) est annulée proprement.
3. **Correction 3.4** : `SuspendedExecution` ne stockait pas le nœud d'entrée — impossible de recompiler la bonne IR après redémarrage. `Ir` porte désormais son `entryNode`, la capture le propage, la reprise recompile depuis lui (révision vérifiée).
4. **BRIDGE-001 (must-fix QA lot 7)** : le pont indexe les nœuds d'entrée par blueprint avec cache invalidé par révision — le coût par émission passe de O(blueprints × nœuds) à O(blueprints) avec comparaison d'entier, reconstruction par blueprint seulement à l'édition ; suppression/ajout/édition testés.
5. `RefResolver` serveur réel (joueurs via la liste, entités via les mondes) ; migrations déjà appliquées par `GraphNbt` (1.4) ; le tout testé headless via une logique de restauration pure (`restore()`) — l'attache `SavedData` réelle se vérifie en jeu (session/1.6).
