# Story 1.1 : Structure multi-module du projet

## Status

Ready for Review

## Story

**En tant que** développeur du mod,
**je veux** que le projet soit découpé en modules Gradle (`api`, `core`, `client`, `compat`, `testmod`),
**afin que** l'API publique consommée par les mods tiers ne puisse pas dépendre de l'implémentation interne.

## Acceptance Criteria

1. `settings.gradle.kts` inclut les sous-projets `api`, `core`, `client`, `compat`, `testmod`, et le build produit **un seul JAR** embarquant `api` + `core` + `client` + `compat`.
2. Le module `api` ne référence aucune classe de `core`, `client` ou `compat` ; une tâche de vérification fait **échouer le build** si c'est le cas.
3. `./gradlew build`, `./gradlew runClient` et `./gradlew runServer` fonctionnent après le refactor.
4. `fabric.mod.json` déclare un entrypoint custom `blueprint` en plus de `main` et `client`, et le mod démarre sans erreur avec zéro plugin enregistré.
5. Les entrypoints existants sont déplacés : `fr.blueprint.core.BlueprintMod` (module `core`) et `fr.blueprint.client.BlueprintClient` (module `client`) ; les logs de démarrage actuels sont conservés.
6. Le module `api` est publiable seul (`./gradlew :api:publishToMavenLocal`) sous `fr.blueprint:blueprint-api`.
7. `options.encoding = "UTF-8"` et le toolchain Java 21 s'appliquent à **tous** les sous-projets.

## Dev Notes

### Contexte du projet existant

État avant cette story (vérifié) :

```
src/main/java/fr/blueprint/BlueprintMod.java          → LOGGER "Blueprint initialisé"
src/main/java/fr/blueprint/client/BlueprintClient.java
src/main/resources/fabric.mod.json                    → entrypoints main + client
src/main/resources/assets/blueprint/lang/{en_us,fr_fr}.json   (vides : "{}")
build.gradle.kts   → Loom 1.13.6, MC 1.21.11, loader 0.18.2, fabric-api 0.139.4+1.21.11,
                     mappings Mojang, Java 21, UTF-8, version 0.1.0, group fr.blueprint
```

**Ne pas casser** : `archivesName = "blueprint"`, `group = "fr.blueprint"`, le commentaire
français expliquant `options.encoding` (il documente un vrai bug Windows/cp1252), les
`vmArg` de `loom.runs`.

### Architecture

- Modules et responsabilités : `docs/architecture.md` §2.3
- Arborescence cible complète : `docs/architecture/source-tree.md`
- Principe P5 « L'API publique ne voit pas l'implémentation » : `docs/architecture.md` §2.1 —
  c'est **la raison d'être** de cette story, l'AC2 n'est pas négociable.

### Points de vigilance

- **Un seul JAR.** Fabric Loom ne gère pas nativement les multi-modules ; la
  configuration retenue est un projet racine avec Loom qui agrège les `sourceSets` des
  sous-projets dans son JAR. Ne pas partir sur cinq JARs remappés séparément.
- Le `remapJar` de Loom doit voir toutes les classes : vérifier le contenu du JAR produit
  avant de clore la story.
- Le module `api` compile contre Minecraft (il manipule `ResourceLocation`, `ServerLevel`…)
  mais **jamais** contre `core`.
- Mappings Mojang : voir la table Mojang/Yarn dans `docs/architecture/tech-stack.md`.

### Testing

- Test de build : `./gradlew clean build` passe, le JAR de `build/libs/` contient bien des
  classes des cinq packages.
- Test manuel : `runClient` démarre, le log `Blueprint initialisé` apparaît, aucun avertissement neuf.
- Test automatisé : la tâche `checkApiIsolation` est couverte par un cas positif (build OK)
  documenté dans le journal de la story.
- Emplacement des tests : `core/src/test/java/...` (JUnit 5, sans Minecraft démarré) —
  voir `docs/architecture/coding-standards.md` §7.

### Completion Notes List

- Pattern retenu : Loom appliqué aux 6 projets (racine + 5 modules), dépendances inter-modules via la configuration `namedElements` de Loom (pattern Fabric API). Le JAR racine agrège les `SourceSetOutput` des 4 modules livrés, puis `remapJar` remappe l'ensemble.
- `gradle.properties` : mémoire Gradle passée de 1G à 2G (6 projets Loom, le remapping en a besoin).
- `checkApiIsolation` est une heuristique sur le pool de constantes des `.class` : toute référence (import, appel, ou littéral de chaîne contenant `fr/blueprint/core|client|compat`) déclenche l'échec. Faux positif possible sur une chaîne légitime — acceptable, il suffira de la composer dynamiquement.
- `duplicatesStrategy = FAIL` sur le JAR racine : un chevauchement de ressources entre modules casse le build au lieu d'écraser silencieusement.
- **Non vérifié : `runClient`** (nécessite une session graphique ; l'utilisateur s'en charge). Le câblage est identique à `runServer`, qui est vérifié. Attendu dans le log client : « Blueprint client initialisé ».
- Warnings cosmétiques au lancement : « Class path entries reference missing files …/resources/main » pour les modules sans dossier resources. Sans impact ; disparaîtront quand ces modules auront des ressources. Ne PAS corriger avec des `.gitkeep` dans `src/main/resources` (ils entreraient en collision dans le JAR à cause de `duplicatesStrategy = FAIL`).
