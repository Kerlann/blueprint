# Story 1.5 : Commande et cycle de vie

## Status

Done

## Story

**En tant que** joueur ou administrateur,
**je veux** `/blueprint list|create|delete|enable|disable|info`,
**afin de** gérer les blueprints du serveur sans passer par l'éditeur.

## Acceptance Criteria

1. Commandes enregistrées via `CommandRegistrationCallback`, autocomplétion des identifiants existants sur `delete|enable|disable|info`.
2. `create` refuse un identifiant déjà pris (message dédié) ; un identifiant syntaxiquement invalide est refusé par le type d'argument (`IdentifierArgument`).
3. Niveau de permission requis configurable (`config/blueprint/config.json`, créé avec ses défauts au premier lancement) ; par défaut niveau 2 (`LEVEL_GAMEMASTERS`) pour `create|delete|enable|disable`, libre pour `list|info`.
4. Tous les messages traduits `en_us`/`fr_fr` (aucune chaîne en dur).
5. La logique de chaque sous-commande est couverte en test unitaire (via `BlueprintManager`) et la **structure de l'arbre Brigadier est vérifiée headless** (sous-commandes présentes, types d'arguments). ⚠ Écart assumé vs PRD : le gametest serveur en jeu est extrait vers une story dédiée « spike gametest » — le framework a été refondu en données en 1.21.5 (`@GameTest` n'existe plus, vérifié au javap) et son infra mérite sa propre story.
6. **MODEL-001 (QA 1.3)** : `enabled` est officiellement un état de cycle de vie serveur (FR20), muté uniquement par `BlueprintManager` — jamais une `EditOperation` ; documenté dans le code.
